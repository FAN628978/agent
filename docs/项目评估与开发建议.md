# 项目评估与开发建议

## 总体结论

当前项目是一个本地 CLI Agent 原型，已经具备基础的工具系统、技能系统、命令系统和 OpenAI 兼容接口封装。

但从测试结果、权限模型、安全边界、文档一致性来看，项目还不适合称为“核心完成”。更准确的状态是：基础框架已搭建，关键契约和安全机制需要尽快补齐。

## 当前可用能力

- CLI 可启动，运行命令：

```bash
uv run python -m src.cli
```

- 启动后当前加载工具：

```text
bash, edit, glob, grep, read, write
```

- 当前加载技能：

```text
code-review, planner
```

- 已有基础模块：
  - `src/agent/`：Agent 主循环、配置、LLM Client。
  - `src/tools/`：工具加载、权限检查、文件读写、搜索、命令执行。
  - `src/skills/`：技能扫描和按需注入。
  - `src/commands/`：CLI 内置命令，如 `/help`、`/clear`、`/exit`。
  - `tests/`：工具系统测试。

## 主要缺点

### 1. 测试当前不通过

执行：

```bash
uv run pytest -q
```

结果：

```text
25 个测试，13 个失败，12 个通过
```

主要失败集中在工具权限系统。

核心原因是权限检查器接口不一致：

- `tests/test_tools.py` 中测试使用两个参数：

```python
lambda name, params: True
```

- `src/tools/loader.py` 实际调用三个参数：

```python
self._permission_checker(name, params, permission)
```

这说明工具权限层的接口契约还没有稳定。

### 2. 工具权限语义不统一

`ToolLoader.execute()` 当前对权限拒绝和工具不存在等情况直接抛出 `ToolExecutionRefused`。

但测试里很多用例期望返回错误字符串，例如：

- 工具未加载。
- 用户拒绝执行。
- ASK 权限无 checker。
- DENY 权限被禁止。

这会导致工具层和 Agent 层职责不清晰。

建议统一为：

- 用户明确拒绝危险操作：可以抛 `ToolExecutionRefused`，让 Agent 停止当前工具调用。
- 普通执行错误、参数错误、工具不存在：返回结构化错误结果。
- 测试按最终契约重写。

### 3. 文件工具缺少工作区边界

以下工具都直接接受任意路径：

- `read`
- `write`
- `edit`
- `grep`
- `glob`

例如：

```python
path = Path(file_path)
```

当前没有检查路径是否在项目工作区内。

风险：

- Agent 可能读取工作区外敏感文件。
- Agent 可能覆盖用户系统文件。
- `write` 会自动创建父目录，风险更大。

建议引入 workspace sandbox：

- 所有路径先 `resolve()`。
- 检查 resolved path 是否位于允许目录内。
- 默认只允许访问项目根目录。
- 对工作区外路径必须显式授权。

### 4. bash 工具风险较高

`bash` 工具会直接执行模型给出的命令。

Windows 下 fallback 还使用：

```python
subprocess.run(command, shell=True, ...)
```

虽然当前有交互确认机制，但还不够。

建议增加：

- 固定工作目录。
- 命令风险分级。
- 拦截明显危险命令，如递归删除、格式化、修改权限、系统级移动。
- 对网络命令、后台服务、包安装命令单独确认。
- 对输出长度做限制。
- 对超时进程做完整清理。

### 5. 敏感文件被 git 跟踪

检查结果显示：

```text
.env
llm_calls.txt
```

已被 git 跟踪。

这有明显风险：

- `.env` 可能包含 API key。
- `llm_calls.txt` 会记录用户输入、系统提示词、工具结果和模型输出。
- LLM 日志可能包含路径、代码、敏感业务内容。

建议：

- `.gitignore` 增加：

```gitignore
.env
llm_calls.txt
*.log
```

- 从 git 跟踪中移除：

```bash
git rm --cached .env llm_calls.txt
```

- 提供 `.env.example`。
- 日志默认关闭，或要求用户显式开启。

### 6. Agent 会话状态不完整

当前工具调用过程只保存在 `request_messages`，没有写回 `self.messages`。

结果是：

- 下一轮对话只能看到最终 assistant 响应。
- 看不到上一轮调用了哪些工具。
- 看不到工具结果。
- 长任务连续执行时上下文容易断裂。

建议把以下内容都纳入会话历史：

- assistant 的 tool_calls。
- tool 的执行结果。
- 最终 assistant 响应。

如果担心上下文过长，应单独设计压缩或摘要机制。

### 7. API 错误处理过粗

`OpenAIClient.chat_with_tools()` 当前捕获所有异常后，都按“本地模型服务未启动”处理。

这会混淆很多错误：

- API key 错误。
- base_url 错误。
- 模型名错误。
- 请求参数不兼容。
- 限流。
- 网络失败。
- 本地模型服务未启动。

建议拆分错误类型：

- 认证错误：直接提示检查 API key。
- 连接错误：再做端口等待。
- 404 / model not found：提示检查模型名。
- 429：提示限流并重试。
- 400：提示请求参数或工具 schema 不兼容。

### 8. 文档与实现不一致

README 中描述的工具包括：

- `calculator`
- `web_search`

但实际项目当前加载的是：

- `bash`
- `edit`
- `glob`
- `grep`
- `read`
- `write`

README 中默认模型写的是 `gpt-4o`，但代码默认模型是：

```python
MiniMax-M2.5
```

另外 `docs/工具加载流程.md` 仍描述旧版 `BaseTool` / `tool` 实例机制，但当前代码已经改成 `TOOL_DEFINITION` + `execute()` 函数。

建议：

- README 只写当前真实能力。
- 规划能力放到路线图。
- 删除或更新过时文档。
- 增加“当前状态”和“未完成事项”章节。

### 9. CLI 打包入口有问题

`pyproject.toml` 中配置：

```toml
[project.scripts]
agent = "src.cli:main"
```

但实际验证：

```bash
uv run agent
```

结果：

```text
program not found
```

同时 `main` 是 async 函数，即使 console script 正常安装，也不适合直接暴露为入口。

建议增加同步 wrapper：

```python
def run():
    asyncio.run(main())
```

然后改成：

```toml
agent = "src.cli:run"
```

### 10. 技能系统还只是提示词注入

技能系统目前主要能力是：

- 扫描 `SKILL.md` frontmatter。
- 根据 trigger 激活技能。
- 将技能内容作为 system message 注入。

但还没有真正执行：

- `allowed_tools` 限制。
- 技能级工具权限。
- 技能资产加载。
- 技能隔离。
- 技能版本兼容校验。

建议短期内不要把它描述成完整技能系统，应称为“技能提示词加载器”更准确。

## 开发建议

### 第一优先级：修复测试和工具契约

先确定工具层契约：

- `execute()` 什么时候返回字符串？
- 什么时候抛异常？
- 权限 checker 是两个参数还是三个参数？
- 工具不存在算异常还是工具执行结果？

建议优先修复：

- `ToolLoader._permission_checker` 接口。
- `ToolLoader.execute()` 的错误返回策略。
- `tests/test_tools.py` 的断言。

目标是让：

```bash
uv run pytest -q
```

全部通过。

### 第二优先级：补齐安全边界

建议新增统一路径工具函数，例如：

```python
resolve_workspace_path(path: str, workspace: Path) -> Path
```

用于所有文件工具。

同时为 `bash` 引入命令策略：

- `ALLOW`：只读命令。
- `ASK`：写入、安装、网络、进程类命令。
- `DENY`：明显危险命令。

### 第三优先级：清理敏感文件和日志策略

建议立即处理：

- `.env` 不应进入 git。
- `llm_calls.txt` 不应进入 git。
- 日志默认关闭。
- 日志应支持脱敏。
- 日志应支持轮转或最大大小限制。

### 第四优先级：完善 Agent 会话历史

建议引入明确的会话消息类型：

- user message
- assistant message
- assistant tool call
- tool result
- system skill activation

这样后续做 memory、审计、回放、debug 都更容易。

### 第五优先级：改进 LLM Client 稳定性

建议增加：

- 请求超时配置。
- 错误类型分类。
- 指数退避重试。
- 流式输出。
- 工具调用最大轮数，避免无限循环。
- token 使用统计。

### 第六优先级：重写 README

README 应该分成：

- 当前能力。
- 快速开始。
- 配置说明。
- 工具列表。
- 安全说明。
- 测试方式。
- 已知限制。
- 路线图。

不要把未来规划写成已完成能力。

## 推荐近期迭代顺序

1. 修复 `ToolLoader` 权限 checker 接口，让测试通过。
2. 统一工具错误处理策略。
3. 给文件工具加 workspace 路径限制。
4. 把 `.env`、`llm_calls.txt` 从 git 跟踪中移除。
5. 修复 console script 入口。
6. 更新 README 和 `docs/工具加载流程.md`。
7. 补 Agent 工具调用历史持久化。
8. 增加 API 错误分类和工具调用最大轮数。

## 当前项目状态判断

| 模块 | 状态 | 说明 |
|---|---|---|
| CLI | 基本可用 | `python -m src.cli` 可启动 |
| Agent 主循环 | 原型可用 | 工具调用可跑，但历史记录不完整 |
| Tool 系统 | 半成品 | 加载机制存在，权限契约需要修复 |
| 文件工具 | 可用但不安全 | 缺少 workspace 限制 |
| Bash 工具 | 可用但高风险 | 需要命令策略和更强确认 |
| Skill 系统 | 原型 | 当前主要是提示词注入 |
| Command 系统 | 基础可用 | 有 help / clear / exit |
| 测试 | 不健康 | 13 个失败 |
| 文档 | 不可信 | 多处与实现不一致 |
| 安全性 | 不足 | 敏感文件、路径、命令执行均需治理 |

## 总结

这个项目的方向是对的，代码规模也还适合继续快速迭代。现在最重要的不是继续加 memory、RAG、MCP 或多 Agent，而是先把工具系统、安全边界、测试和文档打稳。

建议把下一阶段目标定为：

```text
构建一个安全、测试通过、文档真实的本地 CLI Coding Agent MVP。
```

在这个目标完成之前，不建议继续扩大功能面。
